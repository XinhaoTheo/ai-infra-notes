# Kernel 精度验证的失效模式与四类对抗测试

这篇笔记记录的是一个具体问题：当 verifier 用「输出数值误差」来判断一个 kernel 写得对不对时，在某些算子上这套判据会失效。通过Zhuoming的指导，总结了四类专门用来打穿这个盲区的测试场景，目的就是构造出能让现有 preflight（不满足数值误差就 filter 掉）失灵的对抗样例。下面先把贯穿全文的主线讲清楚，再逐类拆开，每一类都给机制和例子。

## 主线：数值误差什么时候不再是「正确性」的忠实代理

现在 verifier 的核心判据，本质上是把候选 kernel 的输出和一个高精度 reference 做对比，看 `|cand − ref|` 是否落在某个容差里（参考 [kernel-agent.md](repos/kernel-agent.md) 里 `torch.allclose(rtol=1e-2, atol=1e-2)` 那一段）。这套判据在 matmul 这类算子上工作得非常好，原因是 matmul 大致保数量级、误差线性传播：输入错一点，输出就错对应的一点，数值误差的大小忠实反映了 kernel 错得多严重。换句话说，对 matmul 来说「数值误差小」和「算得对」几乎是同一件事，数值误差是正确性的一个忠实代理。

问题在于，有一大类算子会**把小的值压扁、抹掉，或者把误差放大**。在这些算子上，「输出数值误差通过了」和「kernel 真的算对了」会分叉成两件事。一旦分叉，验证就会朝两个相反的方向出错，每一类场景你都用这两个方向去套：

一个方向是 **false accept**：kernel 其实算错了，但因为它错的那部分恰好是被算子压没了的小值，最终输出几乎不变，数值误差显示不出来，于是测试报「过」，实际是坏的。另一个方向是 **false reject**：kernel 其实是对的，但因为算子本身太 lossy（比如低精度量化），它的输出和高精度 reference 差得很远，数值误差超出容差，于是测试报「不过」，实际是好的。

四类场景就是围绕「压扁小值」这个统一原则展开的。光去测 matmul 没用，因为 matmul 不压缩小值，bug 藏不住。真正能把验证逼到失效的，是那些会把小值压扁或抹掉的算子。从第 1 类到第 4 类，「数值误差」和「真的算对」之间的缝会越拉越大。

## 第 1 类：softmax / activation

这一类出现在 attention 的 softmax、以及 MLP 里的激活函数（ReLU / GELU / SiLU）。它之所以被排在第一位、也是最基础的一类，是因为 softmax 同时具备两个相反的危险性质，会让验证在两个方向上都出错。

**压扁尾部，导致 false accept。** softmax 的定义是 `exp(x_i) / Σ exp(x_j)`，离 max 越远的 logit，经过 softmax 后的贡献趋近于 `exp(x_i − x_max)`，也就是趋近于 0。举个具体例子：真实 logits 里 key A = 8.0（主导项），key C = 0.5（尾部）。softmax 之后 A 的权重接近 1，C 的权重极小。现在假设候选 kernel 把 C 的 logit 算得离谱——真值 0.5，它算成了 3.0。但 `exp(3) ≈ 20` 跟 `exp(8) ≈ 2981` 一比还是小不点，C 的权重也就从大约 0.05% 变到 0.7%，最终输出 o 几乎不动。结果就是：kernel 在尾部错得一塌糊涂，但输出误差极小，顺利通过验证。错误被 softmax 吃掉了。activation 也是同样的道理——ReLU 直接把负半轴清零，负数上算错多少输出都是 0；GELU / SiLU 在大负值区饱和压向 0。所以这类函数天然有一块「死区」，死区里的错误在输出上完全看不见。

**指数放大头部，导致 false reject。** 反过来，因为有 `exp()`，大 logit 上一点点绝对误差会被指数放大成输出的大误差。还是上面那个例子，假设 kernel 把主导项 A 算得差一点点——真值 8.0，它算成 8.5，误差才 0.5，完全是正常的低精度精度抖动。但 `exp(8.5) / exp(8) = e^0.5 ≈ 1.65`，A 的权重直接涨了 1.65 倍，而 A 主导整个输出，于是 o 偏掉一大截，超出容差，被判错。一个其实没问题的 kernel，被 exp 放大成了「错的」。

**对 verifier 的意义。** 这一类的麻烦在于，你比 pre-softmax（比 logits）还是 post-softmax（比最终 o），用绝对误差还是相对误差，会给出不同的判决，而且没有一个干净的选法。比最终输出 o，尾部和死区里的错误你看不见（放过坏的），头部的小误差又被 exp 放大（冤枉好的）。一个可行的方向是在 activation 之前比、或者针对被压扁的那块区域专门构造输入和加权，但这本身就说明单一的「比最终输出 + 一个容差」在这里不成立。这正是 Zhuoming 说的那条挑函数标准：找一个能把误差拉很大、或者能把值压缩到很小的函数，softmax / activation 就是最典型的。

## 第 2 类：sort / topk

这一类的难点性质和 softmax 完全不同。softmax 输出的是连续值，至少还能谈「数值距离」；而 sort / topk 的输出是一组离散的选择或排列——一组被选中元素的下标。当输出是一组 index 时，`|cand − ref|` 这个量根本就没有定义，两个集合之间不存在「数值距离」。所以这一类最根本的问题是：你平时那招「跟 reference 做数值误差、卡一个容差」在这里压根套不上，你被迫去换一个 surrogate metric，而最顺手抓到的那个 metric 恰好就是 recall（集合 overlap）——你的 top-k 选出来的那一组里，有多少个也落在 reference 选出来的那一组里。下面用 radix top-k 这个真实例子把机制讲透，因为不讲清这个机制，「打平」「换序」「分布依赖」就只是三条散乱的现象。

### radix select 到底在干什么

top-k 常用 radix select 实现。先把 float 做一个单调的 bit 变换（正数翻符号位、负数全翻），让「无符号整数比大小」等价于「float 比大小」。然后从最高位开始，每 8 个 bit 算一个 digit（相当于一个 256 进制的位）：对当前 digit 做直方图，统计每个桶里有多少元素；从高桶往低桶累加计数，找到累计计数跨过 k 的那个桶，叫它**边界桶（boundary bucket）**；比边界桶高的桶里的元素铁定入选，比它低的铁定出局；只对边界桶里的元素，带上接下来的 8 个 bit 递归细分。一个 32-bit 的数，排满 `32 / 8 = 4` 轮就能用完所有 bit，得到精确的 top-k。这里说的「轮」就是这个意思——一轮处理一段 8 bit，4 轮才看完全部 32 bit。

### 近似版错在哪：所有错误只发生在边界桶

近似版（比如 flashinfer / vortex 里那种 approx top-k）只排 2 轮就停，也就是只定了高 16 bit，后 16 bit 不再往下递归，边界桶里的元素直接糊弄过去。关键点在这里：边界桶里的元素高 16 bit 完全相同，这意味着它们的值非常接近，近似版分不出它们谁大谁小，于是要么全收、要么乱挑。所以近似版的错误是**结构性地只发生在 cutoff 附近那条带上**——远高于阈值的、远低于阈值的元素永远判对，只有「卡在第 k 名附近、值彼此非常接近」的那一撮才会乱。

这一句就把三条散乱的现象收编成了同一件事。在 `torch.randn()` 输入下，值又连续又分散，cutoff 附近几乎不会有近到这种程度的两个值，边界带里没几个元素，所以 recall 接近 100%，看着完美——但这个 kernel 本来就不返回精确值，它「过关」不是因为正确，而是因为 randn 这道题太简单，根本没考到它的软肋。而在 BF16 / FP8 输入下，低精度会把大量本来不同的值压成相等（打平），一堆元素挤进同一个 16-bit 桶，边界带一下子变得很胖，recall 就暴跌。所以「打平」和「分布依赖」根本不是两件事，就是「边界带里塞了多少元素」这一件事。

### 为什么这会击穿精度 verifier

第一层，输出是 index 集合，`|cand − ref|` 没有定义，你被迫换一个 metric，而不同 metric 给出不同判决。按选中的值比，边界带里选错一个几乎是零误差（你选了 0.998 而不是 0.999）；按 index recall 比，同样这一次就是一个实打实的 miss。两个 metric 都不绝对正确。第二层，边界处的 ground truth 本身就不唯一。当值打平时，多个 top-k 集合是一样对的，你的 reference（稳定排序）只是钦定了一种 tie-break 顺序；候选 kernel 按另一种顺序选了另一组，两组其实一样对（选中的值完全相同），只是 index 不同，但你拿 index recall 一比就 < 100%，于是一个 bit-exact 的正确 kernel 都可能被冤枉。这就是 false reject 在这一类里的来源：不是 kernel 错，是量化打平加上指标选择联手把它判错了。

### 真正该带走的一点：不是所有 miss 都一样

如果你退化成用 recall 当判据，会踩一个更深的坑：recall 把所有 miss 等权，但不同 miss 的危害天差地别。判断一个 miss 有没有害，真正的标准不是被丢元素的绝对大小，而是**被丢的值和你保留下来的值之间的 gap**。

漏掉一个骑在边界、值约等于 cutoff 的元素，是无害的。因为近似版只能搞错那些和第 k 名值差距在分辨率以内的元素——这撮元素本来就和被选中的 tie-partner 值几乎相等，在下游 softmax 里的权重也几乎一样，丢掉它输出 o 几乎不动。这是设计内的近似误差，不是 bug。具体对照一下：选中集合里最小的 logit 是 5.0，你丢了 4.998、补进来一个 5.001，`exp(4.998)` 和 `exp(5.001)` 差千分之几，o 纹丝不动。

漏掉一个远高于 cutoff 的大值，才是真 bug，而且后果是灾难性的。一个明显大的值，它的高 bit 就明显大，近似版在第一轮就把它铁定确认入选了，正常情况下永远不会丢掉它。它要是真被丢了，只可能来自实现层面的 bug——bit 变换没处理好符号位 / 负数 / NaN / Inf、直方图边界 off-by-one、并行 reduce 的 race、按 fp32 读 bit 但数据其实是 bf16 导致高位读歪，等等。这种 miss 一旦发生，比如一个 logit = 12 的 key 被错丢、换进来一个 logit = 3 的，`exp(12)` 那个主导项没了，o 整个塌掉。

这里有个重要的不对称需要分清楚：**边界 miss 是近似算法的正常产物，远高于 cutoff 的 miss 它结构上根本产生不了**，所以后者一旦出现基本就等于有实现 bug。但要注意，这种实现 bug 产出的是又大又明显的误差，任何数值阈值都一抓一个准，它属于 verifier 正常工作、最不费劲的区域，**不是** verifier 会被骗的地方。verifier 真正的痛点不在这里，而在灰区——误差小到分不清「可接受的近似」和「真的算错」。对应到 topk 这一类，真正危险的 false accept 不是某个 coding bug，而是：一个过度激进的近似，只在 randn 这种 benign 分布上验证过、下游误差很小、看着就是对的，于是被放过；可它换到真实分布（有结构、有打平、有主导 key 的长尾）就会漏掉重要 key。它的问题不是「写崩了」，而是「只在送分分布上验过」，这种 distribution-dependent false accept 才是要拿去喂 Claude Code 让它构造的东西。

所以这一类的正确判法不是「数对了几个 index」，而是按被丢元素相对保留集合的 value gap 加权：gap 约等于 0 不罚，gap 大重罚——这样天然把「无害的边界 swap」和「灾难性的大值漏选」分开了。极端一点的做法是干脆别比 index，直接比最终的下游输出 `softmax(q@k[I]/√d)·V[I]`，让正确性回到一个有数值距离的量上。

## 第 3 类：softmax / activation + FP8

这一类是第 1 类的「压扁」再叠一层低精度。要先抓住低精度格式的关键性质：它能表示的数特别少、量化格子特别粗。FP8 的 E4M3 只有 3 个尾数位，每个 2 的幂区间里只能表示 8 个值。格子一粗就有两个直接后果——两个本来不同、但差得比格子还小的值会被 snap 成同一个码（强制打平）；小于最小可表示档位的值直接变成 0（flush to zero）。这两条是这一类和下一类所有坑的根。

它比单独的第 1 类更狠，因为「压扁」这件事现在编进了数字格式本身。

**双重抹掉，导致更强的 false accept。** softmax 已经把尾部概率压到很小（比如 0.001、0.0012、0.0008 这种量级）。再用 FP8 去存这些值，这个量级附近 FP8 能表示的码就那么几个，于是这三个本来不同的概率可能全被 snap 成同一个 FP8 码、或者干脆都变 0。这意味着「尾部到底算对还是算错」在 FP8 里根本编码不出来——一个尾部全错的 kernel，输出跟正确的逐 bit 相同，误差严格为 0，白送过关。第 1 类是 softmax 这个运算把错误藏起来，值本身还是全精度；第 3 类是连藏的空间都没有了，格式本身表示不了那点差别。

**逼你开大容差，踩中 preflight。** 反过来，一个正确的 FP8 kernel，跟 FP32 reference 一比，误差本来就很大（毕竟只有 3 个尾数位，exp、求和在 FP8 下的量化和累加顺序都会引入难以 bound 的误差）。你为了让这个对的 kernel 通过，必须把容差开得很大。可一旦开大，「正确但 lossy 的 FP8 kernel」和「真有 bug 的 kernel」就落进了同一个容差带，分不开了。这正是 preflight 的核心两难，下面单独讲。

## 第 4 类：low bit（FP4 / INT4）

这一类把第 3 类推到极端，格子粗到离谱，两个失效方向同时崩到底。FP4 的 E2M1 每个区间只有 2 个可表示值，INT4 全程一共就 16 个等距档位。

**误差直接 round 成 0，false accept 到极致。** 这就是 Zhuoming 说的「差个 0.0X 直接消失」。两个值只要差得比量化步长小（4-bit 下步长巨大），量化后就 snap 成完全相同的码。于是一个在高精度下会出问题的算法、或者一个算出略微不同中间结果的 kernel，在 FP4 / INT4 下给出逐 bit 一样的输出，误差严格为 0，毫无悬念地通过。这次不是某个运算把错误藏起来，是这个表示根本没有地方放下这个差别，bug 彻底隐形。另外，低于最小可表示档位的小值还会直接 flush 成 0，任何作用在这些小值上的计算都与输出无关，处理错了也看不见。

**正确 kernel 却跟参考差到天上，false reject 到极致。** 一个正确的 INT4 kernel，输出跟 FP32 reference 一比误差大得惊人，任何「紧」的容差都会把所有实现全 reject 掉。到这一类，拿 bit 级数值误差去判这条路基本走不通了——你要么做量化对量化的比较（但那样参考又该取谁？），要么干脆放弃逐元素数值误差，改用下游 / 任务级指标（看模型整体输出还好不好）。

把第 1、3、4 类串起来看是一个递进：第 1 类是 softmax 这个运算把小值的错误藏起来，值本身全精度；第 3 类是运算藏 + FP8 格式根本表示不了那点差别，还逼你开大容差；第 4 类是格子粗到误差直接归零（放过坏的到极致），正确 kernel 又跟 FP32 差太远（冤枉好的到极致），数值误差作为判据彻底失效。第 2 类则是另一个轴：它的正确性根本不是一个数值量，而是离散选择，连「用误差衡量」这个前提都不成立。

## 贯穿四类的核心两难：preflight 的容差 trade-off

把第 3、4 类暴露出来的矛盾单独拎出来讲，因为这是整套 verifier 最难处理、也最该被对抗测试逼出来的地方。现在的流程是做一个 preflight：候选 kernel 不满足数值误差就直接 filter 掉。Zhuoming 指出这里有个根本性的 trade-off，没法用一个阈值卡死。

一边是 false reject：低精度 kernel（FP8 / INT4，以及近似 topk）本来是对的，但很难满足紧的数值误差。为了让这些对的 kernel 过，你不得不把容差开大。另一边是 false accept：容差一开大，它就不再是「数值误差」了，而是变成了「实际误差」——一个真正算错的 kernel，可以用别的方式钻这个松掉的容差蒙混过关。

所以本质矛盾是：**有些 kernel 满足数值误差但其实是错的，有些不满足却是对的**；为了救 topk / FP8 这种「实际对但被判错」的情况而去放宽容差，代价就是放进来更多假阳性。这两类（该放过的 lossy kernel、该杀的 bug）落在同一个容差区间里，单调一个 magic number 永远分不开。这说明 preflight 不该是一个标量阈值，而应该是 multi-agent 判定逻辑里专门处理的一个分支：根据算子类型切换判据（连续输出比数值误差、topk 这种选择类按 value-gap 加权或直接比下游输出、低比特退化到任务级指标），而不是所有 kernel 共用一个 `allclose` 容差。

## 和 attention 例子的联系：一个现成的多盲区目标

sparse attention 恰好把前面几类叠在一起，是个现成的、能同时踩到多个盲区的验证目标。普通 dense attention 不用 top-k——`o = softmax(q@kᵀ/√d)·V`，每个 query 对所有 key 都算权重。top-k 出现在 sparse attention 里，目的是省算力：长上下文下 key 特别多（几万、几十万），但 softmax 算出来其实只有少数 key 权重大，对所有 key 都算太浪费。于是 sparse attention 先看一下分数 `q@k/√d`，只挑出分最高的 k 个 key，只对这 k 个做 softmax 和加权和，其余直接扔掉，也就是 Zhuoming 那张图里的式子：

```
o = softmax(q@k[I]/√d) · V[I],   I = top-k 选出的 2000 个 key 的下标
```

这里 `I` 就是用（近似）top-k 选出来的那 2000 个 key 的下标，`[I]` 表示「只取这些 key」。你要验的那个 kernel 干的就是这件事（对应高效推理方向里的 Quest、vortex 这一类）。

这个目标的迷惑性在于它同时踩了多个点。`I` 这一步是第 2 类（top-k 选择），后面的 `softmax` 是第 1 类（压扁），而测试时大家图省事用的输入又正好是 `torch.randn()`——这是所有分布里最 benign、最送分的那一个。具体说，测试时手头没有真模型，也不需要，只要一组形状和 dtype 对的数就能跑 kernel，于是直接 `torch.randn(B, H, N)` 造一组随机数当假 logits 顶上去。但真实的 attention logits 根本不长这样：真实数据有扎堆、有主导 key 的长尾，BF16 / FP8 下还有大量打平。结果就是一个只在 randn 上验过的近似 attention kernel，可能漏掉权重大的重要 key，但 verifier 因为只在 benign 分布上测过，把它放了过去。这就是前面反复出现的 distribution-dependent false accept，在这个例子里 top-k 的「压扁」和 softmax 的「压扁」还会叠加，盲区更深。

## 落到对抗测试：给 Claude Code 的构造方向

把四类组织成可以直接喂给 Claude Code 的测试构造任务时，每一类都按「往哪个方向失效（放过坏的 / 误杀好的）＋ 触发它的具体输入构造」这两栏来写。统一的反思路是：别再拿 `torch.randn` 这种送分输入测（它又连续又分散、几乎不打平），而是专门去构造能踩中各类软肋的分布。

针对 softmax / activation，构造让主导项和尾部 logit 差距极大的输入，专门往尾部 / 死区注入错误，看 verifier 是否放过；同时构造主导项上的小扰动，看是否被 exp 放大成误杀。针对 sort / topk，构造大量打平和 cutoff 附近扎堆的分布（包括 BF16 / FP8 量化后离散的值），把 randn 藏住的边界带问题逼出来，并区分「无害的边界 swap」和「漏掉远高于 cutoff 的大值」这两种性质完全不同的 miss。针对 softmax + FP8，构造尾部概率全落进 FP8 同一个码或 flush 到 0 的输入，验证尾部错误是否被双重抹掉，同时确认正确 FP8 kernel 是否会因容差太紧被误杀。针对 FP4 / INT4，构造真实差距小于量化步长的输入，验证误差是否被 round 成 0 而隐形，并确认数值误差判据是否已经退化到必须改用下游 / 任务级指标。
