# KernelEvolve: Scaling Agentic Kernel Coding for Heterogeneous AI Accelerators at Meta

- 论文：[arXiv 2512.23236](https://arxiv.org/abs/2512.23236)
- 作者：KernelEvolve Team @ Meta（一作 Gang Liao；通讯 Carole-Jean Wu / Gaoxiang Liu）
- 类型：production deployment paper（不是研究 paper，是部署报告，正文 41 页 + 18 页 conv1d kernel 源码）

## One sentence pitch

把 LLM 包成生产级 agent 给 NV / AMD / MTIA 自动写 Triton kernel；用 graph-based search + retrieval-augmented prompting + 持久化 KB；在 KernelBench 250/250 通过、480 个 operator-platform 配置 100% 正确、生产负载相对 PyTorch 加速 1.2–17×；开发周期从 weeks 压到 hours。

## Motivation

三维度叠加 -> O(operators × hardware) 组合爆炸，手写不可能。

1. **Hardware heterogeneity**：跨厂商（NV warp/SM vs AMD wavefront/CU vs MTIA PE 阵列+RISC-V）、跨代际（Ampere -> Hopper 的 TMA / WGMMA / warp-group 是新的 execution model 不只是新指令）、内存层级差异。**关键：差异在 execution model 层面，不是语法层面**。
2. **Model diversity**：1500+ 生产模型，retrieval / early / late ranking 三阶段；late stage Transformer-based ranking（Wukong / InterFormer / HSTU）~80 GFLOPS/req，比传统 dense 重 10-100×。
3. **Kernel primitive diversity**：**不只是 GEMM**——200+ 数据预处理算子（bucketize、jagged ops、cryptographic hashing、top-k）。算术强度低，但架构上是 first-class 关键。

### Binary deployment constraint

> 缺一个预处理的kernel = 整个模型不能在加速器一体化部署就会被迫拆 disaggregated（CPU 层 + 加速器层）。

**Table 2 里面的量化论证**：一体化的P99 = 61ms，拆分之后的P99 = 97ms, δ = α − β − γ ≈ 10–20ms 是**纯网络税**，没有任何计算价值。多种代价叠加打击比如序列化、级联故障、运维同步、TCO 上升

**反直觉论点**：小算子缺失（architectural penalty）> 大算子慢一点（incremental degrade）-> 预处理算子优先级 >= GEMM。

## 系统架构（3 + Figure 5）

### Graph-Based Search 形式化（3.1）

四元组 `(F, π_sel, O, τ)`：

- **F (fitness)** = `t_pytorch / t_triton`；编译失败或 numerical mismatch -> 0
- **π_sel** = greedy / MCTS / evolutionary，可切换
- **O (universal operator)** = 单一变异函数 + 动态 prompt（**不是**多个静态算子模板）
- **τ** = wall-clock / step budget / 收敛阈值

### 关键设计 1：Universal Operator（3.1）

不用传统 Draft / Debug / Improve 多算子（每个静态 prompt），而是**一个 universal operator + 检索增强动态 prompt**。理由：

- 静态 prompt = cognitive constraint，提前框定 LLM 的思考方向
- 真实 bottleneck 通常混合（既有 numerical bug 又有 memory pattern 问题），单一 lens 看不全
- 让 LLM 根据 runtime artifact 自由判断是 debug 还是 perf 问题

### 关键设计 2：Two-Stage Retrieval（3.2）

两个子 agent 串成一条 pipeline：

**Context Memory Sub-Agent**：分析 runtime artifacts（当前 kernel 代码 + profiling 数据 + 错误诊断 + correctness 结果）-> 诊断 bottleneck -> 输出 optimization directive（比如"register spill + bank conflict"）。

**Deep Search Sub-Agent**：根据 directive 从 persistent KB 做 targeted retrieval（比如取 `hardware/nvidia/optimization/register_optimization.md`）。

两步输出汇总成合成动态 prompt，后续喂给 universal operator 调用的 LLM。注意其中的核心原则是**检索目标必须由 runtime context 决定**，不能盲目检索。先诊断再给出具体的解决方案，避免 context 被泛泛知识淹没。

### 关键设计 3：Persistent Knowledge Base（3.2.1）

目录结构：

- `content/constraints/` —— 硬约束：禁用 CUDA API、禁用外部库
- `content/guidance/` —— 跨平台优化技巧
- `content/hardware/amd/`
- `content/hardware/mtia/` —— MTIA 闭源知识，LLM 训练时没见过
- `content/hardware/nvidia/arch/`
- `content/hardware/nvidia/optimization/` —— tma.md, persistent_kernel.md
- `content/hardware/nvidia/tlx/` —— warp_spec.md, async_tensor_core.md
- `content/hardware/nvidia/code_samples/`
- `content/index.md` —— 总目录，做 retrieval 入口

**用文件系统层级 + index.md 当检索信号**，不用 embedding。理由是（1）知识本身是层级化的（NVIDIA->optimization->TMA），目录结构天然编码语义,比 embedding 更精确（不会把 "NVIDIA TMA" 和 "AMD memory access" 混淆）(2) 直接 git 管理，写文档即更新，不用维护 vector index

优化早期检索基础概念（tensor_cores.md），中期检索高级特性（TLX warp spec），后期直接看完整 code sample。

### 关键设计 4：双层持久化存储（3.2.2）

- **Metadata Store（关系数据库）**：`id / pid / score / is_buggy / path_ref` 五列，pid 编码树结构
- **Object Store（对象存储）**：每个节点对应一个目录，存 `kernel_N.py` + `overview.md`（LLM 写的分析报告）

这会带来 4 个能力：
1. **并发探索**：多 agent 同时扩不同节点，DB 提供事务隔离
2. **复杂查询**：用 SQL 递归 CTE 做图遍历（找祖先链上 > 1.5* 的策略）
3. **跨会话复用**：以前优化过的同类算子直接当起点，省 token和算力
4. **Fault tolerance**：每次节点插入即原子 checkpoint，几小时长跑崩了能恢复
research类型prototype 全没这个能力（1.1 批评的 6 条之一就是 no checkpointing）。

### 关键设计 5：MTIA Knowledge Injection（3.2.3）

解决 LLM 没见过 MTIA 的问题——通过文档而非 fine-tune。**普适性**：新硬件出来可以直接写文档进KB，不用重训 LLM

MTIA 教材内容：

- libdevice API（`tl.extra.libdevice.gelu` -> SFU LUT，硬件级查找而非软件实现）
- 编译选项（`cb_multiplier` 扩 Circular Buffer、`use_dual_core` 让 core A 跑 DMA / core B 跑向量）
- Compute helpers（`unary_elemwise_compute` 直接编译到向量指令）
- 跨 PE 通信原语（`tl.load(direction="down")` 邻居广播、`tl.pe_runtime_barrier()` 全 PE 同步、`tl.copy()` 显式拷贝防 race）
- 自定义类型（`TensorView`、`CoreID`、`ExecutionGrid`）

### 工程组件（3.3 – 3.4）

- **AI Hardware Interpreters**：每种硬件一个 Bento 环境（NV / AMD / MTIA），Conveyor 自动每天重建跟上 Triton 编译器版本
- **Code Generator for Evaluation**：确定性 Python 程序生成评测脚手架，**不token写模板代码**——LLM 只生成核心 kernel 逻辑
- **Triton MPP（Multi-Pass Profiler）**：解决 profiler 互相干扰问题。base trace + targeted probe（隔离单条指令）+ guarded instrumentation + result fusion；对 TMA / warp-spec / async copy 这类异步操作能拿到 instruction-level 数据
- **Agentic JIT Debugging**：emit C++（`emit_cxx=True` 拿到 RISC-V 前的 C++ 中间产物）-> 修改 -> `replay_cpp` 跳过 Triton 重编译，迭代周期从分钟到秒
- **FaaS Evaluation**：CPU-bound 生成 vs GPU-bound 评测解耦。生成 agent 跑本地 CPU，评测 dispatch 到 FaaS 上的远端 GPU/MTIA pool；解决"100 个生成 agent 抢 8 张本地卡"的资源错配

## Triton 选型（1 + Figure 2-3）

为啥选 Triton 当主 DSL：

- 用户层只写一份 Triton Code（LLM 只学一种 DSL）
- 编译器先 lower 到平台无关的 Triton-MLIR
- 然后分叉成 TritonGPU / TritonAMDGPU / TritonMTIA dialect（在编译器内部完成跨平台分裂）
- 再降到 LLVM-MLIR / LLVM-IR
- 最终生成 PTX/CUBIN（NV）、AMDGCN/HSACO（AMD）、RISC-V Binary（MTIA）

跨平台分裂被编译器内部消化了，**LLM 只需要会一种 DSL + 知道每种硬件的特性**。

## Evaluation

### OSS 验证（4）

- KernelBench 250 道题（3 难度）100% 通过
- 160 个 ATen 算子 × 3 平台 = 480 配置 100% 正确
- ATen 算子的 fitness 改进有限（torch.cos 2.8->3.05、add.Tensor 0.64->0.70），因为基础原语本身没多少 headroom

### Conv1d 案例（5.1）

- Production shape (2048, 96, 96, 200)、FP16 vs `torch.conv1d` 2.30×、vs 优化的 `conv2d` 1.62×
- 优化点：**fusion 消除 layout 转换**（conv2d 路径要 unsqueeze + channels-last + squeeze）+ autotune 20+ 配置 + 双缓冲 + cache modifier（`.ca` 流式、`.cg` 复用）
- 搜索 300 步，fitness 从 ~2000 涨到 6889
- **反例**：out-of-distribution shape 上反而慢（0.49–0.63×）-> 用 shape-aware dispatch 兜底，过分布外 fallback 到 PyTorch

### Conv1d 跨硬件（5.2）

- AMD MI300: 1.75× / NV A100: 1.77× / AMD MI350: 2.54× / NV H100: 2.30× / MTIA v3: **6.54×**
- MTIA 加速比最大 -> 因为 vendor library 在 MTIA 上不成熟，自动生成的 headroom 大（vendor library 越成熟，自动生成相对收益越小）

### MTIA 数据预处理（5.4）

双重价值：

- **Enablement**：MTIA v2i 缺 `clamp.out` / `gather.out` / `_unique2` / `unique_consecutive` 等 ATen 算子，PyTorch fallback 到 CPU -> 不能跑；KernelEvolve 给出可用实现
- **Optimization**：MTIA v3 已经有这些算子，但 KernelEvolve 通过 fusion + vectorized counting + adaptive blocking 仍能 2–3× 加速

### Batch Event Truncate（5.5）

- Jagged tensor 操作，PyTorch 没有 batched 实现（每个 feature 串行 loop）
- KernelEvolve 自动生成 batched Triton kernel
- 9.8× 加速，**重点是生成出原本不存在的 batched 实现，不只是优化已有代码**

## 与竞品的差异（1.1 + 7）

竞品：KernelBench / AutoTriton（清华，RL）/ KernelLLM / CWM（Meta 自家早期）/ TritonRL（Amazon）/ GEAK（AMD）/ Kevin（Cognition AI，CUDA RL）/ AlphaEvolve（DeepMind，TPU/GPU 进化）/ TritorX。

6 条 production gap（每条对应 KernelEvolve 一个章节）：

1. **Narrow scope**：只 RL 训练或单步生成，无 end-to-end lifecycle -> KernelEvolve 整个 3
2. **Synthetic eval**：玩具 benchmark 没真实负载（jagged tensor、hashing）-> KernelEvolve 5 case studies
3. **Single platform**：只 NV -> KernelEvolve 3.2.3 + 多硬件
4. **Limited agent**：缺多层验证 / 层次化 profiling / 持久化 KB -> KernelEvolve 3.2 + 3.4
5. **No inference-time scaling**：不做几百到几千轮搜索 -> KernelEvolve 3.1 tree search
6. **No checkpointing**：崩了从头来 -> KernelEvolve 3.2.2 metadata store
